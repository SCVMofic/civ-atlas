# Civ Atlas 下一阶段实施计划（Agent 执行版）

> **目标**：优先补齐外交系统闭环，再修复浏览器后退导航，最后实现历史编辑前后的差异摘要。所有改动必须保护模拟确定性、续跑一致性和旧存档兼容性。
>
> **仓库**：`SCVMofic/civ-atlas`

## 0. Agent 总指令

开始前阅读
`README.md`、`docs/simulation-resume-contract.md`、`docs/upstream-integration-2026-10.md`（若存在）、`package.json`，以及相关模拟、存档、历史编辑、导航和测试代码。

必须遵守：

1.  **先调查后编码**：先确认现有数据流、API、测试与功能，不得臆造数据结构。
2.  **保护确定性**：同一版本、seed
    和输入应维持既有可观察输出一致性。没有充分证据时，不改
    RNG、事件队列排序、同 tick 调度顺序或模拟核心流程。
3.  **遵守续跑契约**：遵循 `docs/simulation-resume-contract.md` 对
    ChangeLog、编年史、检查点、最终文化/政体图层等可观察输出的约定；不要把内部处理器执行顺序擅自升级为契约。
4.  **兼容旧存档**：新增字段使用安全默认值、可选字段或显式迁移；缺字段不得导致崩溃。
5.  **不伪造历史**：编年史与差异摘要只能陈述数据能够支持的事实。证据不足时保守表达或不展示。
6.  **小步交付**：各阶段独立修改、测试和报告。不得将多个阶段混成不可审查的大改动。
7.  **控制范围**：不包含多人联机、月份/季节模拟、宗教、贸易或模拟架构重写。
8.  **保留仓库保护**：不要无关地更改
    attribution、上游链接、部署目标或部署工作流保护条件。

每阶段结束时汇报：变更文件与目的、行为变化、测试与命令结果、风险/未完成项、是否建议进入下一阶段。若现有架构与计划冲突，先报告证据和替代方案，不得静默改变契约。

## 1. 执行顺序

  阶段      优先级   任务                 交付
  --------- -------- -------------------- ------------------------------------
  Phase 0   必须     现状盘点与基线测试   代码位置、功能缺口、测试基线
  Phase 1   P0       外交系统闭环         关系影响决策；战争与和平结果可追溯
  Phase 2   P1       浏览器后退导航       Back 返回合理的上一个应用视图
  Phase 3   P1       历史编辑差异摘要     以真实数据比较编辑前后变化
  Phase 4   P2       回归、文档、收尾     测试通过，文档反映真实实现

建议按顺序执行。每阶段应可独立审查/回滚。如果现有外交系统已实现部分闭环，应优先补缺口和测试，而不是重写。

## 3. Phase 1 --- 外交系统闭环（主功能）

### 目标

形成完整、可追溯的流程：外交关系影响决策 → 战争开始 → 战争结束/和平 →
政治或领土结果 → 编年史准确记录。

### 3.1 数据与状态

先检查现有模型，只有在确实不足时才新增字段。根据现有架构评估以下概念：国家关系、联盟/互助承诺、附庸/宗主与朝贡关系、战争状态及参战方、战争起因/目标、和平结果、领土归属变更记录。

-   [ ] 明确各状态的创建、更新、终止条件。
-   [ ]
    防止非法状态，例如循环附庸、已灭亡政体仍有有效联盟、战争结束后仍处于战争状态。
-   [ ] 复用仓库已有稳定 ID 体系；确保新增数据可序列化。
-   [ ] 为旧存档提供安全默认值或迁移。
-   [ ] 避免保存容易与权威状态失同步的冗余数据。

### 3.2 让外交关系影响模拟决策

-   [ ] 联盟对援助或避免交战产生至少一项明确、可测试的影响。
-   [ ] 联盟破裂/背约具有清晰的状态转移和记录，不得只改 UI 标签。
-   [ ] 附庸/朝贡关系影响政治状态，或在现有经济模型支持时影响资源流向。
-   [ ] 外交决策使用可复现的规则，不依赖非确定性的随机遍历顺序。
-   [ ]
    如果项目没有可靠经济/资源系统，不要虚构复杂经济机制；先完成政治关系和可追溯记录，将经济效果列为后续事项。

### 3.3 战争、和平与领土结果

-   [ ] 每场战争能识别参战方及开始/结束状态。
-   [ ] 只有存在可靠结构化依据时才记录战争起因；不得推测动机。
-   [ ] 战争结束记录实际结果，而非只有含糊的结束文本。
-   [ ] 和平造成领土转移时，记录地区 ID、转移前后归属和关联事件。
-   [ ] 若和平改变附庸/政治地位，记录实际发生的变化。
-   [ ] 无领土转移时，不得生成割地叙述。
-   [ ] 记录可保存、恢复，并供编年史和后续差异摘要使用。

### 3.4 编年史

-   [ ] 战争条目表达参战方；有可靠起因时才表达起因。
-   [ ] 结束条目表达可验证的结果；只有系统能判定胜负时才写胜负。
-   [ ] 领土变化指出地区及前后归属。
-   [ ] 附庸/朝贡变化有明确叙述。
-   [ ] 文案与结构化事实一致，数据不完整时使用保守表述。
-   [ ] 遵守既有时间和事件排序契约，不擅自改变同 tick 执行顺序。

### 测试清单

-   [ ] 联盟创建、维持、解除及其对模拟决策的影响。
-   [ ] 附庸/朝贡关系创建、终止和非法状态防护。
-   [ ] 战争开始、结束状态正确。
-   [ ] 和平割地记录前后归属正确。
-   [ ] 无割地的和平不会生成虚假割地记录。
-   [ ] 编年史与结构化事件一致。
-   [ ] 保存并重载后，外交状态和历史记录一致。
-   [ ] 对相关续跑场景做回归并比较可观察输出。
-   [ ] 固定 seed 回归若有差异，必须说明原因、范围和预期性。

### 验收标准

-   [ ] 外交不只是展示标签，而会影响至少一项可验证的模拟决策。
-   [ ] 战争---和平---政治/领土结果形成可追溯链路。
-   [ ] 编年史不与结构化事实矛盾。
-   [ ] 新旧存档安全处理。
-   [ ] 相关测试、类型检查、lint/build（以仓库实际脚本为准）通过。
-   [ ] 无未经解释的 RNG、事件调度或续跑契约变化。

### 本阶段不做

不做完整外交谈判 UI、复杂外交 AI
重写、贸易/宗教/季节模拟或多人联机；不为文案丰富度编造战争动机。

## 4. Phase 2 --- 浏览器后退导航修复

### 目标

用户从地图进入国家、人物、战争、编年史或编辑视图后，浏览器 Back
应返回合理的上一个应用视图，而非意外离开站点或丢失上下文。

### 任务

-   [ ] 先定位导航机制并复现问题，记录最小操作步骤。
-   [ ] 使用符合当前架构的最小修复；不为单个问题贸然引入大型路由依赖。
-   [ ] 覆盖直接打开、刷新、连续打开多个详情、Back 和 Forward。
-   [ ] 防止 `pushState` 与状态更新互相触发造成历史记录循环。
-   [ ] 明确弹窗/临时面板是否进入浏览器历史，并保持行为一致。
-   [ ] 在当前架构支持的范围内保留地图、选中实体和滚动上下文。

### 测试与验收

-   [ ] 从主视图打开详情，Back 返回主视图。
-   [ ] 连续打开多个详情，Back 按顺序返回。
-   [ ] Forward 能恢复刚离开的视图（若架构支持）。
-   [ ] 刷新或直接访问深层链接不会进入损坏状态。
-   [ ] Back 不会因应用内导航逻辑意外跳出站点。
-   [ ] 无重复历史项、无限循环或状态更新警告。
-   [ ] 现有测试和构建通过。

## 5. Phase 3 --- 历史编辑前后差异摘要

### 目标

历史编辑后，让用户理解哪些内容发生变化。所有摘要必须来自真实数据，而非模型猜测。

### 5.1 比较策略

-   [ ] 先检查是否已有编辑前后快照、变更日志或稳定实体 ID。
-   [ ] 优先比较结构化数据，不直接依赖自然语言编年史全文差异。
-   [ ] 使用稳定 ID 匹配实体；若无
    ID，先定义明确匹配规则与不确定性，不要仅凭可能重复的名称合并实体。
-   [ ] 将新增、移除、修改、无法可靠匹配分开处理。
-   [ ] 明确比较对象是"编辑前快照 vs 编辑后结果"。
-   [ ]
    不把模拟自然演化误称为编辑的直接因果结果；无法区分时标为"前后结果差异"。

### 5.2 可展示类别

只展示底层数据支持的项目：

-   新增或消失的国家/政体；
-   政体名称、统治者或其他已有结构化字段的变化；
-   战争新增、结束或结果变化；
-   王朝、人物、重要事件变化（仅限现有数据模型支持）；
-   最早可观察差异年份（仅当数据完整、计算规则明确时）。

### 5.3 实现要求

-   [ ] 将差异计算实现为无副作用的纯函数（若现有架构允许），输入
    before/after，输出类型明确的差异对象。
-   [ ] UI 负责展示，避免在展示层进行复杂事实推断。
-   [ ] 大型世界提供折叠或限制摘要长度。
-   [ ] 不修改原存档，不消耗或改变 RNG 状态。
-   [ ] 对旧存档、缺字段和缺 ID 安全降级。
-   [ ] 不引入远程 AI 服务或外部依赖，除非维护者另行批准。

### 测试与验收

-   [ ] before/after 相同，差异为空。
-   [ ] 新增、删除实体正确识别。
-   [ ] 已有实体字段变化正确识别。
-   [ ] 不同 ID 的同名实体不会被错误合并（如果模型提供 ID）。
-   [ ] 缺字段/缺 ID 时不崩溃、不产生虚假结论。
-   [ ] 最早差异年份有明确规则和测试。
-   [ ] UI 摘要与差异对象一致。
-   [ ] 计算差异不改变模拟状态、存档或 RNG 状态。

## 6. Phase 4 --- 回归、文档与收尾

-   [ ] 从 `package.json` 确认并运行测试、类型检查、lint、build 命令。
-   [ ] 运行模拟确定性、续跑和存档兼容相关测试。
-   [ ] 检查新增状态的序列化、反序列化、默认值与版本兼容。
-   [ ] 仅勾选 README 中已实现并验证的路线图事项。
-   [ ] 更新相关文档，说明外交状态、存档和续跑约束。
-   [ ] 补充简洁的用户说明（若行为对用户可见）。
-   [ ] 确认 attribution、上游链接、部署工作流保护条件未被无关修改。
-   [ ] 清除临时日志、调试代码和无用依赖。
-   [ ] 汇报未完成项和后续建议，不把未实现功能写成已完成。

最终验收：

-   [ ] 各阶段测试命令和结果已记录。
-   [ ] 无未经解释的确定性/续跑回归。
-   [ ] 旧存档不会因新增字段而崩溃。
-   [ ] 各阶段解耦，便于单独回滚。
-   [ ] 文档只反映已实现并验证的行为。
-   [ ] Agent 提供变更文件清单、测试结果、风险与建议。

## 7. Git 与交付建议

建议每个 Phase 独立提交，遵循仓库现有提交规范。可参考：

1.  `docs: add agent implementation plan`
2.  `feat: complete diplomacy event and peace outcomes`
3.  `fix: preserve in-app navigation on browser back`
4.  `feat: summarize history edits`
5.  `test/docs: cover compatibility and update roadmap`

不要把计划文档与核心模拟逻辑混在同一提交。未经明确授权，不要直接推送、合并
PR、删除分支、修改 GitHub Actions secrets 或启用旧站部署。

**先只执行 Phase 0，不要立即修改代码。**
阅读指定文档，检查相关实现与测试，运行基线测试，提交一份带文件路径和证据的现状盘点报告。报告确认最小安全改动路径后，再进入
Phase 1。每完成一个
Phase，都先报告结果并等待维护者确认是否继续，除非维护者明确要求连续执行全部阶段。
